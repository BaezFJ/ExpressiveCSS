# ExpressiveCSS accessibility rules

## Rules

Reuse the root version resolution and the selected component's rules. `semantics.json` owns package markup rules; it does not establish WCAG conformance.

1. Prefer documented native elements: buttons for commands, links with real `href` values for navigation, and native dialogs, inputs, labels, and groups.
2. Authors own elements, landmarks, labels, decorative hiding, and initial state the contract explicitly requires at author time. Components own changing ARIA values and generated IDs when their contract says so.
3. Label every navigation landmark. Do not use `<nav>` for card actions, toolbars, app-bar commands, or other button rows.
4. Use `<span class="material-symbols" aria-hidden="true">` for decorative icons, or screen readers can announce the ligature word.
5. Name icon-only controls, with `aria-label` when needed; tooltips supplement names.
6. Do not add composite roles such as `menu`, `tablist`, or `toolbar` unless the component documentation declares the role and the promised keyboard model is implemented. Use APG to verify behavior a declared role promises.
7. Keep hidden subtrees out of the focus order. `aria-hidden="true"` does not remove descendants from Tab navigation.
8. Connect every form label, supporting text, error, group legend, and description to its control with native relationships.
9. Use correct button types inside forms, useful image `alt` text, and empty `alt` for decoration.
10. Localize every user-facing string generated by component options; do not hard-code English in framework source.

## Material recommendations and WCAG criteria

Report Material recommendations, WCAG success criteria, and observed browser behavior separately. Material's 48 by 48 dp touch-target recommendation is not WCAG 2.2 AA's 24 by 24 CSS-pixel minimum with exceptions. Measure the clickable region, not the icon or hardware pixels, and preserve the component's larger target contract.

Read the [focused web checks](./references/web-checks.md) when the affected flow includes targets, dragging, hover or focus content, text spacing, obscured focus, authentication, contrast, or forced colors. Read only the relevant sections. Matching color-role names and keyboard-only dragging alternatives are not proof of accessibility.

## Verification

Inspect the browser accessibility tree and operate the affected flow. Check keyboard operation and visible focus order; dialog focus, containment, Escape, and return; names, values, and descriptions; feedback; measured contrast and target size; reduced motion, zoom, reflow, and content extremes; and light, dark, and relevant user overrides. Fix each failure, then rerun the checks it could affect.

Record measured values, state, browser, and criterion or recommendation separately. Tree inspection does not prove spoken announcements; emulation does not certify an OS and assistive-technology combination. Mark unavailable checks honestly. Run the consuming project's checks; framework changes also need applicable semantics and interaction tests.
