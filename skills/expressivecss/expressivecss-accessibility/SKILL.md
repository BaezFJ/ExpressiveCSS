## ExpressiveCSS accessibility rules

Read the selected component guide, then the target version's semantics contract. In this repository, `semantics.json` is normative and `SEMANTICS.md` is generated from it.

1. Start with the documented native element. Buttons run commands; links with real `href` values navigate; `<nav>` contains destinations; `<dialog>`, `<input>`, `<select>`, `<progress>`, `<fieldset>`, and `<label>` keep their native contracts.
2. Authors own static semantics: element choice, landmarks, labels, decorative hiding, and only the initial state that the target-version documentation explicitly requires at author time. Components own changing values such as `aria-expanded`, `aria-selected`, and generated IDs when their contract says so.
3. Label every navigation landmark. Do not use `<nav>` for card actions, toolbars, app-bar commands, or other button rows.
4. Use `<span class="material-symbols" aria-hidden="true">` for decorative icons. The ligature is real text and is otherwise announced.
5. Give every icon-only control an accessible name, normally `aria-label`. Use a tooltip as additional visible explanation when no adjacent text explains the action.
6. Do not add composite roles such as `menu`, `tablist`, or `toolbar` unless the component documentation declares the role and the promised keyboard model is implemented.
7. Keep hidden subtrees out of the focus order. `aria-hidden="true"` does not remove descendants from Tab navigation.
8. Connect every form label, supporting text, error, group legend, and description to its control with native relationships.
9. Use correct button types inside forms, useful image `alt` text, and empty `alt` for decoration.
10. Localize every user-facing string generated by component options; do not hard-code English in framework source.

## Required browser checks

The semantics contract covers element choice, landmarks, and implied ARIA. It deliberately does not prove the following, so test them separately:

- keyboard operation for every action and state;
- visible focus and logical focus order;
- dialog initial focus, containment, Escape behavior, and focus return;
- accessible names, roles, values, descriptions, and live announcements;
- 4.5:1 normal-text contrast, 3:1 large-text contrast, and 3:1 non-text UI contrast;
- 48 by 48 dp target guidance;
- reduced-motion behavior;
- zoom, reflow, and high-content states.

Use WAI-ARIA APG to verify behavior a role promises, not to add a role that ExpressiveCSS withholds or rejects.

## Verification

Inspect the accessibility tree in a real browser, complete the flow keyboard-only, test light and dark themes plus reduced motion, and run the consuming project's accessibility checks. For framework changes, run the semantics suite and the component's generated-accessibility or interaction tests as applicable.
