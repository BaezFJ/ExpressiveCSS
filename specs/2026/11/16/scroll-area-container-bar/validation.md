# Scroll area container bar: validation

Phase 101: draw the bar on a scroll container. Requirements: [requirements.md](requirements.md). Plan: [plan.md](plan.md).

Implementation starts from `0b0493f2840dcc11ba8b670a5d995b9d146fc79a`, after master integration. The rows below call it the start commit. Phase review base remains `40ab4fb74044d1b9a45ba10494c5a9fc8d8668b1`.

## Agent-run checks

Commands: `npm run build`, then `node --test tests/scroll-area.test.js` for the jsdom checks and `EXPRESSIVECSS_TEST_BROWSER=<engine> node --test tests/scroll-area-container-browser.test.js` once per engine for the browser checks.

Browser checks use a 600 by 500 window and a 1,500px-tall document, so the page can scroll. Unless a row says otherwise the fixture is `<div id="host"><p id="before">Before</p><div id="box" class="scroll-area custom" style="block-size: 300px; inline-size: 240px"><div style="block-size: 900px"></div></div><p id="after">After</p></div>`, with no border or padding on the container. There `clientHeight` is 300, the thumb is 100px long, its travel is 200px and the scrollable distance is 600px, so one pixel of pointer travel scrolls 3px. A y coordinate in a row is measured from the bar's top edge.

jsdom checks set `clientHeight` 300, `scrollHeight` 900, `clientWidth` 240 and `scrollWidth` 500 on the container. They stub a recording `ResizeObserver`, the frame queue, and `scrollTo` and `scrollBy` on the container and the window. jsdom 31's own `CSS.supports` returns true for anchor positioning. A row that needs the real `MutationObserver` says so.

## Review record

- 2026-11-16, spec review by one independent read-only subagent (a Plan agent). It was given the three files, the constitution, the phase 99 and 100 specs, the source and reader paths and the base commit `40ab4fb74`, without the author's reasoning, and it ran the risk pass against the source instead of tracing the existing IDs. It ran one read-only probe against the installed jsdom and no build, test or browser. Every result above stays pending, and every statement about anchor positioning, paint order and scroll reset in this spec is unverified in a browser until the checks run.
- Two read-only scouts surveyed the code and its readers before the spec was written. The author confirmed their claims that the spec cites by reading the files.
- The review returned 32 findings: 3 blockers, 20 to fix and 9 nits. The author checked each against the source. 29 were confirmed and fixed in full, and 3 were fixed in part, with the rest of each rejected below.
- Confirmed and fixed:
  - The framework's own scrolling bodies didn't clip the bar, although the supported markup puts containers inside them. R24, its decision and V16 now cover the scaffold's pane, a dialog's body and a pane's body.
  - V4's numbers ignored the framework's `border-box` sizing (`src/sass/base/_global.scss:11`). The border case now expects a 294px track and a 94px thumb.
  - R17 and V13 compared serialized markup, which jsdom rewrites when an inline style is touched. They now compare nodes, order and inline declarations.
  - A container that overflows only sideways lost its native bar. R12 now hides the native bar only while the drawn bar is displayed.
  - jsdom 31's `CSS.supports` returns true for anchor positioning, so the constraint, the reader note and R23 were wrong about the unsupported path. The support test is now per instance, as `scrollArea.ts:97` does it.
  - Plan groups were out of order: the display rule moved into group 2, V15 into group 4, and group 4 now needs group 3.
  - Sharing the page bar's rule would have broken a page assertion R23 keeps. Container rules are now separate.
  - The press needed the pointer's `clientY` relative to the bar (R14, V10, plan group 4).

### Native move and media decision

The milestone owner authorized checking a native state-preserving move before accepting the focus boundary, then clarifying the reachable-focus contract if no portable move existed. The [DOM standard](https://dom.spec.whatwg.org/#dom-parentnode-movebefore) defines `moveBefore()` on ParentNode, including Element, Document and DocumentFragment. It moves without removal and preserves associated state. [MDN's API documentation](https://developer.mozilla.org/en-US/docs/Web/API/Element/moveBefore) includes focus among those states and distinguishes native audio/video play state, which survives ordinary removal and reinsertion, from iframe loading state.

The sequential probe ran after the visual suite completed, `/tmp/p101-review-native-move.log`. Chromium 158.0.8127.18 and Firefox 159.0 expose the method on Element, Document, DocumentFragment and ShadowRoot. Both retained a closed descendant's focused input through wrapping and unwrapping in connected Element and closed-ShadowRoot parents. Their detached DocumentFragment moves restored the nodes without an exception; detached content has no active focus to preserve. WebKit 27.2 exposes none of those methods, and each attempted variant throws TypeError. Ordinary insertion remains the shared strategy; no optional native branch was added.

The next isolated probe used the actual built component, `/tmp/p101-review-native-state.log`.
