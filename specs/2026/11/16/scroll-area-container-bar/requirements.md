# Scroll area container bar: requirements

- Feature: `ScrollArea` on a scroll container wraps it and draws the page bar's vertical bar at the container's inline-end edge
- Date: 2026-11-16
- Roadmap phase: [Phase 101: draw the bar on a scroll container](../../../../roadmap.md#phase-101-draw-the-bar-on-a-scroll-container), the third phase of the milestone "custom scrollbars". It depends on phase 100. The [mission](../../../../mission.md#product-rules) keeps markup compatibility and accessibility contracts stable and makes behavior changes opt-in. The [tech stack](../../../../tech-stack.md#framework-stack) lists CSS anchor positioning among the native features to use before script, with a fallback where an engine lacks one.
- Branch: `feature/2026-11-16-milestone-custom-scrollbars`. The milestone ships as one pull request, which the milestone run owns, so this phase adds no branch.
- Base: `40ab4fb74044d1b9a45ba10494c5a9fc8d8668b1`. Phases 99 and 100 are built, reviewed and pushed at this commit and merge with the rest of the milestone. Their specs, [page bar](../scroll-area-page-bar/requirements.md) and [drag and track](../scroll-area-drag-track/requirements.md), are the accepted baseline here. The roadmap keeps their unfinished labels until the merge.

## Current behavior and need

`ScrollArea` draws a bar only on `<html class="scroll-area custom">`. Its constructor returns at `src/ts/components/scrollArea.ts:20` for any other element, so `<div class="scroll-area custom">` gets an instance that adds nothing, and the container keeps the utility's themed native bar. The AutoInit registry already claims those elements: its selector is `.scroll-area.custom` (`src/ts/components/registry.ts:89`), and `tests/fixtures.js` uses a `div` for the fixture.

A page that opts in gets one bar style for the document and another for every scroll box inside it. The docs, `llm.md`, the hand-written skill reference and the `semantics.json` note all say the modifier is page-only.

The bar's thumb length, drag and track press read `clientHeight`, `scrollHeight` and `scrollTop` from `this.el`, so the metrics already fit a container. Five things in the current code are tied to the page:

- The bar is a `position: fixed` child of `<html>`, styled through `html.scroll-area.custom > .scroll-area-bar`.
- Drag and track press scroll through `window.scrollTo` and `window.scrollBy`.
- The press compares the pointer's `clientY` with the thumb's offset directly (`scrollArea.ts:52`), which is right only for a bar that starts at the top of the window.
- `.scroll-area-thumb` takes `animation-timeline: scroll(root block)` wherever the engine has scroll timelines. That rule matches any thumb, so a container's thumb would follow the page's scroll.
- The scroll listener of the fallback path is on the window.

## Scope

- A container path in `ScrollArea`: the wrapper, the bar, the measurements, the scroll target, wheel forwarding on the bar, and restoration in `destroy()`.
- Styles for the wrapper and the container bar in `src/sass/utilities/_scroll-area.scss`, and a narrower selector for the root scroll timeline.
- One `position` declaration in each of `_scaffold.scss`, `_dialog.scss` and `_panes.scss`, applied only to a body that holds a wrapper.
- `semantics.json`, the docs page, `llm.md`, the hand-written skill reference, the AutoInit tables, the CHANGELOG entry and gzip budget lines.
- jsdom and browser tests in Chromium, Firefox and WebKit.

## Exclusions

- The horizontal bar (phase 102). Until then a wrapped container whose vertical bar is drawn shows no bar for sideways overflow, because one rule hides both native bars. A container that overflows only sideways keeps its native bar (R12). The milestone ships both phases in one pull request. Wheel, keys and touch still scroll sideways.
- Hover and pressed appearance (103), idle hiding (104), marks (105) and the drag label (106).
- `custom` on an element that a parent's direct-child rule sizes or scrolls: the scaffold's pane, a dialog's body, a pane's body and the others R21's audit finds. See the decision below.
- A `<dialog>` or `[popover]` element as the container. It enters the top layer and its bar would not.
- A scroll timeline for the container's thumb, and state-preserving DOM moves through `moveBefore`.
- New options, events or public methods.
- The page bar's behavior, its clearance property and its stacking token.
- Roadmap completion state, which the milestone records after merge.

## Decisions

Every decision here was made under delegation from project evidence. The user has not reviewed them.

| Decision | Status | Reason |
| --- | --- | --- |
| The wrapper is `<div class="scroll-area-wrapper">` with `display: contents`, so it takes over nothing. The container stays the flex or grid item of its original parent and keeps its own margins (the roadmap's open question). | Decided from evidence | A wrapper with a box would need the container's margins, flex and grid placement copied onto it. `getComputedStyle` returns used pixels for `margin`, `width` and `height`, so `margin-inline: auto` and `height: 100%` can't be copied, and a copy goes stale at the next breakpoint. `display: contents` removes the wrapper's box, and the container's box becomes a child box of the original parent again. `wrapInControl` in `core/formControl.ts:58` wraps an input this way for the same reason, for Chips and Cascader. Restoration then has no layout style to undo. |
| The bar is `position: absolute` and takes its place from the container through CSS anchor positioning, with one anchor name per instance | Decided from evidence | A wrapper without a box can't be the bar's containing block. Offsets measured in script go stale when a sibling above the container grows, which resizes neither box. The tech stack names anchor positioning, `Utils.setAnchorName` and `Utils.guid` exist for Tooltip, Menu and HoverCard, and the three installed test engines support it (Playwright 1.65.0 with Chromium 158, Firefox 159 and WebKit 27.2, read from `node_modules/playwright-core/browsers.json`). `tests/popover-browser.test.js:96` records the same fact. |
| Where `CSS.supports('anchor-name: --a')` is false in the instance's window, a container instance adds nothing and the native bar stays | Decided from evidence | The tech stack asks for a fallback. The themed native bar is the fallback the utility already gives without the runtime, and an instance that doesn't wrap can't change the layout. The test runs per instance through the element's window, as `scrollArea.ts:97` tests scroll timelines, so an iframe and a test can each answer for themselves. |
| The wrapper's `display: contents` is `!important` | Decided from evidence | An author rule such as `.panel > div { display: flex; padding: 8px }` has higher specificity than a class and is unlayered, so it would give the wrapper a box and move the container. The wrapper is the framework's element and has no other supported display. No test bans `!important`. |
| The bar overlays the container's padding box at the inline-end edge and reserves no gutter. The roadmap says "beside it". | Decided from evidence | Phase 99 made the page bar an overlay, and the roadmap asks for "the same bar". A wrapper without a box has no room beside the container. |
| A container instance doesn't set `--scroll-area-bar-clearance` | Decided from evidence | The property inherits. Set on a container it would move every `.back-to-top` and `.fab-menu` inside by 18px from the window's edge, although the page has no bar there (`_back-to-top.scss:18`, `_fab-menu.scss:52`). Content at a container's edge is the author's, and the docs give the padding that keeps a control clear. |
| The container's thumb follows a passive `scroll` listener on the container in every engine | Decided from evidence | The thumb is outside the scroller, so `scroll()` can't find it, and a named timeline needs `timeline-scope`, which no source in `src/sass` uses and no test covers. The listener path already exists, is frame-coalesced, and meets the 1px tolerance one frame late (phase 100's R4). A timeline can replace it later without changing this contract. |
| A wheel over the container's bar scrolls the container through a `wheel` listener on the bar | Decided from evidence | The bar is the container's sibling, so the engine would scroll the container's parent, and the pointer rests on the bar after a drag. Phase 100's R3 gives the page bar the same result natively. The listener cancels only what it forwards, so a wheel at the container's end chains to the ancestor as a native one does. |
| The bar takes the container's computed `z-index` when it isn't `auto`, and has none otherwise | Decided from evidence | The page token, 999, would lift a container's bar over a sticky app bar the container scrolls under. With the container's own value, or `auto`, the bar paints directly above the container, because it follows the container in tree order. Without the copy, a container with `z-index: 1` would cover its bar while its native bar is hidden. |
| The native bar hides only while the drawn bar is displayed, through `:has(+ .scroll-area-bar:not([hidden]))` | Decided from evidence | A container that overflows only sideways has a hidden vertical bar, and hiding its native bars would leave it with none until phase 102. `:has()` is already used in `_navbar.scss` and in the page rule. |
| Scroll offsets and focus are saved before each move and put back after it | Decided from evidence | Wrapping and unwrapping remove the container from the document for an instant. An engine may reset its scroll position, and a focused element inside loses focus, which would drop a keyboard user to the top of the page. `lightbox.ts:106` restores focus the same way after its own unwrap. |
| `custom` isn't supported on an element that a parent's direct-child rule sizes or scrolls, and `semantics.json` forbids it | Decided from evidence | `.scaffold > :is(main, .scaffold-pane)` (`_scaffold.scss:225`), `dialog > div` (`_dialog.scss:135`) and the pane rules at `_panes.scss:71` and `:262` match by direct child. A wrapped container stops matching and loses its grid area, flex sizing and padding, and the wrapper `div` matches in its place. Wrapper-aware selectors in each component are a separate change. The supported markup puts a `.scroll-area.custom` element inside those bodies. |
| The scaffold's pane, a dialog's body and a pane's body get `position: relative` while they hold a wrapper | Decided from evidence | The three are scroll containers without a `position`, and the supported markup puts wrapped containers inside them. The bar's containing block would then lie outside the body, and the body would not clip the part of the bar that the container has scrolled past. `:has(.scroll-area-wrapper)` limits the change to pages that opted in. An author's own scrolling ancestor is the author's element, so the docs give the same declaration for it. |
| The registry and its selector stay as they are | Decided from evidence | `claimed()` already returns `.scroll-area.custom` containers, and the constructor is what ignored them. Phases 99 and 100 are unreleased, so no released page changes behavior. |
| No options, events or methods | Decided from evidence | Nothing here is configurable. `refresh()` keeps its name and gains the container's measurements. |

## Technical constraints

- The container path reuses the bar element, the metrics and the pointer handlers of phases 99 and 100. The page path keeps scrolling through its window.
- The page bar's rule `html.scroll-area.custom > .scroll-area-bar` keeps its declarations in one rule. `tests/scroll-area-bar-browser.test.js:78` finds that rule by `position: fixed` and reads `touch-action` from the same body, and `tests/shadow-dom.test.js:85` pins the clearance rule's body. Container rules are separate rules placed after the page rules.
- Listeners take `this._events.signal`. The component reads the document and window through `this.el.ownerDocument`.
- Each new function stays below cyclomatic complexity 5 (the fallow pre-commit gate), and the phase exports nothing new.
- A custom property that only script sets needs a `var()` fallback, or `tests/tokens.test.js` fails.
- The bar holds no text or icon, so its sizes stay in pixels.
- jsdom 31 has no layout, and its `CSS.supports` returns true for `anchor-name: --a`. A container instance therefore wraps in jsdom, `tests/autoinit.test.js` included, and the unsupported case stubs `supports` to return false. `tests/setup.js` stubs `ResizeObserver` and `Element.prototype.scrollTo`.
- Tests run against the built bundles and tear instances down in `finally` blocks.

## Requirements

Structure

- **R1** `ScrollArea.init(el)` on an element that has a parent node and is neither `<html>` nor `<body>`, in a window with anchor positioning, inserts one `<div class="scroll-area-wrapper">` where `el` was, moves `el` into it as its first child, and appends one `<div class="scroll-area-bar" aria-hidden="true">` holding one `<div class="scroll-area-thumb">` after `el`. The wrapper has no role, no ARIA attribute and no `tabindex`, and neither the bar nor the thumb is focusable. The component writes nothing on `el` except one entry in its inline `anchor-name` list, and it leaves `el`'s children alone.
- **R2** An instance adds nothing, registers no listener or observer and leaves the native bar alone when `el` is `<body>`, when `el` has no parent node, or when `CSS.supports('anchor-name: --a')` is false in its window. `destroy()` on such an instance is safe. This replaces phase 99's R12. The page path on `<html>` is unchanged and doesn't depend on anchor positioning.
- **R3** The wrapper has `display: contents !important` in every medium, print, forced colors and coarse pointers included. Where no selector styles the container through its parent or siblings, the container's border box and the boxes of its siblings are the same before `init`, while the instance lives and after `destroy()`, within 0.5px. That holds in block flow with auto margins and a `max-inline-size`, as a flex item with `flex: 1` and `min-block-size: 0`, as a grid item with a named area and with a span class in `.row`, with a percentage `block-size`, and for an absolutely positioned container. An author rule that matches the wrapper by a child selector doesn't give it a box.
- **R4** A wrapped container that has a `slot` attribute gives the wrapper the same `slot` value, so the container stays in its named slot.
- **R5** `init` and `destroy()` keep the container's `scrollTop` and `scrollLeft`, without animation when the container has `scroll-behavior: smooth`. When the active element is the container or inside it, it has focus again after each call. A container with a role and an accessible name keeps both.

Bar

- **R6** While the drawn bar is displayed, it is `position: absolute` and anchored to the container. Its box spans the block range of the container's padding box, is `var(--scroll-area-bar-size, 12px)` wide, and lies against the padding box's inline-end edge, inside the border. The side follows the container's computed `direction`, so `dir="rtl"` on the container or on an ancestor puts the bar on the left. `--scroll-area-bar-size`, `--scroll-area-thumb-color` and `--scroll-area-track-color` set on the container or on an ancestor apply to its bar. The bar's `z-index` is the container's computed value when that isn't `auto`, and `auto` otherwise. The thumb keeps the page bar's 8px width, rounded ends and colors.
- **R7** The thumb's length and offset follow phase 99's R5 and R6 with the container's `clientHeight`, `scrollHeight` and `scrollTop`. A 300px-tall container with 900px of content has a 100px thumb, a third of the track, and at the end of the content the thumb's end touches the track's end. An instance that starts on a container already scrolled shows the right offset before any scroll event.
- **R8** The container's thumb follows the container's scroll through one passive `scroll` listener on the container, in every engine, writing at most once per animation frame. It doesn't follow the page's scroll: the root scroll timeline applies only to the page bar's thumb. The page path is as phase 99's R7 left it, with no `scroll` listener on the window where the engine has scroll timelines.
- **R9** The bar stays on the container's edge without script when layout moves or resizes the container, such as a sibling above it growing, and when an ancestor scrolls, including an ancestor scroller that has no `position`, and while the container is sticky.
- **R10** The thumb's length and offset update without a scroll when the container's box resizes, when one of its element children resizes, when its direct children are added or removed, and on `refresh()`. Each measurement also rereads the container's direction, border widths, `z-index`, visibility and the three custom properties of R6. A change to one of those that resizes nothing, and text added to a text node that is the container's direct child, show at the next measurement, and the docs name `refresh()` for them.
- **R11** The bar has the `hidden` attribute when the container can't scroll on the block axis, because `scrollHeight` is not greater than `clientHeight`, because its computed `overflow-y` is `hidden` or `clip`, or because its computed `visibility` is not `visible` at a measurement. It loses the attribute at the next measurement that finds the container scrollable and visible. A container that isn't rendered, such as one in a closed dialog, measures as unscrollable and is measured again when it gets a box. A container that is no longer the wrapper's child also measures as unscrollable.
- **R24** A wrapped container inside the scaffold's pane, a dialog's body or a pane's body has a bar that the body clips: the part of the bar above or below the body's scrollport is not painted and takes no pointer. Each of the three bodies has `position: relative` while it contains a wrapper and keeps its current computed `position` otherwise. The same holds inside an author's scroller that has a `position`.

Native bar and media

- **R12** Under `screen and (forced-colors: none) and (not (pointer: coarse))`, a wrapped container that has the `custom` class and whose bar lacks `hidden` has `scrollbar-width: none` and `display: none` on its `::-webkit-scrollbar`, and its bar is displayed. In every other case the drawn bar has `display: none` and the container keeps the utility's native bar: without an instance, after `destroy()`, after `custom` is removed from the container, while the bar has `hidden`, under forced colors, with a coarse primary pointer and in print. Restoring `custom` shows the drawn bar again. A container that overflows only sideways keeps its native bar.
- **R13** A container instance sets no `--scroll-area-bar-clearance`. On a page without the page bar, a `.back-to-top` or `.fab-menu` inside a wrapped container keeps its 16px inset, and the page rules of phase 100's R12 and R13 are unchanged.

Pointer

- **R14** The container's bar takes the pointer as phase 100's R1, R2, R4 to R8 and R10 specify, with the container in the document's place and the pointer's `clientY` measured from the bar's top edge. A press in the thumb's block range starts a drag that sets the container's block scroll position without animation and leaves its inline position alone. A press outside that range scrolls the container by its `clientHeight` once, toward the press, following the container's own `scroll-behavior`. Dragging through half of the thumb's travel scrolls half of the container's scrollable distance. Neither gesture scrolls the page or any ancestor, at the container's ends included. A primary press leaves focus and the selection alone; other buttons retain native behavior. The page bar's hit test gives the same results as before.
- **R15** With the pointer over the container's bar, a wheel scrolls the container by the event's `deltaY` and `deltaX`. Pixel deltas apply as they are, a line counts as 40px and a page as the container's `clientHeight`. The listener forwards and cancels an event only when the container can scroll in the direction of the event's larger delta. Any other wheel, and a wheel with Ctrl held, is neither forwarded nor cancelled, so page zoom and scroll chaining stay with the engine. The page bar gets no `wheel` listener.
- **R16** A drag on a container's bar ends on release, on `pointercancel` and on lost capture, and also when the bar stops being displayed, when the bar's media conditions change, when `custom` is removed, when a modal dialog that doesn't contain the container opens, and when an ancestor gains `inert`. After any of these, pointer moves scroll nothing until a new press. A container inside an open modal dialog drags as any other.

Lifecycle

- **R17** `destroy()` ends a drag, cancels a pending frame, disconnects the observers, removes the listeners and the bar, and replaces the wrapper with its remaining child nodes, so the container has its original parent and its original previous and next siblings. The parent then holds the same nodes in the same order as before `init`. `destroy()` removes its own `anchor-name` entry and keeps the author's inline declarations, and a container that had no `style` attribute has none afterward. It throws nothing when the container was taken out of the wrapper, when the wrapper is disconnected, when the instance never wrapped, and when it runs twice, and in each case no wrapper or bar of that instance stays in the document. A second `destroy()` on an instance that a later `init` replaced leaves the later instance's wrapper and bar in place. While an instance lives and its container has been moved out of the wrapper, the container shows its native bar and the instance's bar has `hidden` from the next measurement.
- **R18** Initializing twice, or `AutoInit()` after an explicit `init`, leaves one wrapper, one bar and one instance, and never a wrapper inside a wrapper. `AutoInit(context)` starts every `.scroll-area.custom` container in the context, `.no-autoinit` opts one out, and the registry and the page claim of phase 99's R14 are unchanged. With `watch: true`, wrapping a container neither destroys nor duplicates its instance, and removing the container or an ancestor destroys the instance and leaves no wrapper in the removed markup. `destroy()` on a container that still matches the selector puts it back in the watched context, so the watcher starts it again, as it does for any matching markup that is added. Removing `custom` or adding `.no-autoinit` first keeps it unwrapped.
- **R19** The page instance, several container instances and a container nested in another are independent. Each bar has its own anchor name and sits on its own container, and a drag scrolls only its own container. An instance in an iframe uses the iframe's window. A container in a shadow root whose only stylesheet is the framework's draws and drags its bar.
- **R20** `ScrollArea` gains no option, event or public method.

## Risks considered

- Two at once. Two `init` calls, AutoInit after `init` and a replaced instance's late `destroy()` are R17 and R18. Several instances, nesting and iframes are R19. `destroy()` during a drag is R17, and a second pointer during a drag is phase 100's R2, inherited by R14. A watcher and an explicit `destroy()` on the same element are R18. A container moved while its instance lives is R17.
- Bad input. `<body>`, a parentless element and a window without anchor positioning are R2. A container that can't scroll, isn't rendered or isn't visible is R11. A container shorter than 48px has a thumb as long as its track, so it has no travel and no track to press, and the wheel, keys and touch scroll it (phase 100's R4). Parents that can't hold a `div`, and top-layer elements, are R21.
- Refusal. The phase adds no permission or data boundary.
- Readers. The docs, `llm.md`, the skill reference, the AutoInit tables, the semantics note and rule, the skill test's phrases, the budget lines and the pins are R21 to R23. `tests/fixtures.js` keeps its `div` fixture, which jsdom now wraps, and R23 keeps `tests/autoinit.test.js` passing unmodified. `BackToTop` and `ScrollSpy` read the window, which a container's bar never scrolls. No component in `src/ts` or `src/sass` puts `.scroll-area` on an element it generates.
- UI states. RTL is R6. Forced colors, coarse pointers and print are R12, and the wrapper keeps the layout in each (R3). Without JavaScript there is no wrapper. Reduced motion: the component animates nothing, and a track step follows the container's `scroll-behavior`. Enlarged text changes the content's height, which R10 measures. Modal dialogs and `inert` are R16, and nested scrollers are R9, R19 and R24.
- Layout shift. On a system with classic scrollbars, hiding the native bar widens the container's content once at `init`, as phase 99 documents for the page. The border box doesn't change (R3).
- Selectors and scripts that see the wrapper. This is the cost of wrapping. The container becomes the wrapper's first child and is never its last. R22 documents it, and R21 forbids the parents where the framework's own rules or HTML's content models depend on a direct child.
- Moving the container. Scroll offsets and focus are R5. Putting focus back fires `focus` and `focusin` again, which a listener such as Autocomplete's sees as a new focus. The other effects are item 2 of R22. Ordinary insertion is used in every engine so the behavior is the same in each.
- An observer on the parent. A component that watches its children sees the wrapper arrive at `init` and leave at `destroy()`. The AutoInit watcher is R18, and R23 runs every other component's tests.
- The bar outside a scroller. The bar's containing block is the nearest positioned ancestor. When a scrolling ancestor between the two has no `position`, that ancestor does not clip the bar. R24 covers the three framework bodies that the supported markup points to, and item 4 of R22 gives authors the same declaration for their own scrollers. The framework doesn't set `position` on an author's element, because the author didn't opt that element in and the change would move its other absolutely positioned descendants. The other framework scroll containers keep their computed `position`, and an author who puts a wrapped container in one applies item 4.
- The frame after the container loses its box. When the container becomes `display: none`, the measurement that hides the bar runs a frame later, and for that frame the bar has no anchor. Plan group 2 probes whether a thumb paints in that frame and adds a rule if one does.
- Stacking. The container's own `z-index` is R6. Positive `z-index` content inside the container paints over the bar, and item 5 of R22 gives `isolation: isolate`. The framework doesn't set it, because it changes how the container's content stacks against the page.
- Target size. The bar is 12px wide, so WCAG 2.5.8's spacing applies to controls at the container's edge as it does at the page's. The framework can't see a container's content, so item 7 of R22 documents the 18px padding, the same distance phase 100 gives its own controls.
- Rounded corners. The bar is a sibling, so the container's `border-radius` doesn't clip it. The track is transparent by default and the thumb is 8px wide and centered in the 12px bar, so a thumb at either end can cross a large radius by a few pixels.
- Anchor names. The component adds its name to the inline list and keeps the author's inline names (R17). An `anchor-name` the author's stylesheet gives the container loses to the inline list while the instance lives, as it does on a Tooltip or Menu trigger.
- The author styles the bar by accident. A rule such as `.panel div { margin: 8px }` matches the bar and thumb. The page bar has the same exposure to `div` rules, and the phase protects only the wrapper's display.
- Wheel forwarding. A line step of 40px approximates each engine's own, and forwarded steps are instant. A container with `overscroll-behavior: contain` still chains from its bar at the ends, because the bar is outside it.
- Observation cost. The component observes each element child of the container, so a container with thousands of direct children gets as many observations. The documented long list, `.defer-render` in `lists.astro`, is one child of its scroll area.
- Writing modes. The bar is vertical and the thumb moves on the y axis, as on the page. A container with a vertical writing mode is not supported.
- `specs/checklist.md`: the project has none.


## Decisions made while building

- All three engines kept a sticky container's bar on its edge through parent scroll positions 0, 100, 200 and 400px, with zero top-edge difference. Sticky is supported and V6 now asserts it. Fixed containers remain outside the contract.
- Headless Firefox reports computed `scrollbar-width: none` even when an uninitialized element has inline `scrollbar-width: thin`. The existing native utility test records this engine limitation. V8 and V17 retain their Firefox markup, media, matched CSS and scrolling checks; Chromium and WebKit also assert computed scrollbar width. This qualifies an unavailable headless measurement, not native OS scrollbar appearance.

- V9 checks field focus and selection before a native right-click, as the unchanged page-bar test does. All engines blur the input on a native right-click. The check still asserts that the right-click neither scrolls nor cancels the context menu. Primary drag and track gestures preserve the engine-specific pregesture selection string, input focus and selection range, and do not select paragraph text.

- The semantics audit uses the affected child selector, not a blanket exclusion of its parent. A middle generic container in `.prose`, an ordinary `article > div`, and `.row > .s6` remain supported. The audit and its negative fixtures name each structural relationship in validation.md.
- Additional R17 regression checks found that `Utils.setAnchorName` alone drops an explicit `anchor-name: none` declaration and the original declaration priority. The container path now preserves both while continuing to remove only its own anchor name. V13 covers author names, `none`, and `!important` declarations.

- After the idle regression removed repeated ResizeObserver resets, the true next-frame probe exposed a painted 48px thumb with a missing anchor. The bar now has an explicit anchor-size height with a zero fallback; the thumb's maximum height is that track height. V7 retains the original zero-rect assertion in all engines. `position-visibility: anchors-valid` was probed and rejected, because it did not hide the thumb consistently.
- A style change can remove the anchor's box before the queued measurement. R16 therefore observes `style` as well as the planned attributes and checks the container's height. The observer also watches the container's own shadow root. A second open modal requires checking every modal, rather than only the first match. V12 covers the held-rAF, shadow-host inertness and second-modal cases.
