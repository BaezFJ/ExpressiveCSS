## Increment 2 findings

The first browser run passed 22 of 24 checks; Chromium and WebKit rejected the test's assumption that the same closed-select ArrowUp/Tab sequence commits a native option in every engine. Replacing Tab with Enter still failed those two checks. A temporary diagnostic established that Chromium and WebKit use the shipped `appearance: base-select` and focus an OPTION when opened; Firefox uses `auto` and retains SELECT focus. Opening only the customizable picker with Space, then sending ArrowUp/Enter through `page.keyboard` without locator refocusing, passes. No runtime or stylesheet fix was needed. Logs: `/tmp/expressivecss-phase70-browser-keyboard-first.log`, `/tmp/expressivecss-phase70-browser-keyboard.log` and `/tmp/expressivecss-phase70-native-picker-probe.log`. The diagnostic was removed. The final browser run passes all 75 checks.

The new static regression failed before adding the page-size rules. A further regression showed that the shared accessible-name helper incorrectly accepted option text as the select's name, including inside a blank label. The source helper now reads native labels while excluding their descendant selects, and does not fall back to option text. The same helper is regenerated into the MCP package. Native labels and aria-labelledby pass; unnamed controls, blank labels, multiple selects and wrong elements fail without initialization. Logs: `/tmp/expressivecss-phase70-semantics-red.log` and `/tmp/expressivecss-phase70-semantics-label-red.log`.

Guidance verification ran `node --test tests/semantics.test.js tests/docs-astro.test.js tests/expressivecss-component-decisions.test.js tests/expressivecss-skill.test.js`, followed sequentially by selective-build and generated checks.
