# Drop-zone type validation requirements

Phase 72, 2026-10-27. Branch `feature/2026-10-27-drop-zone-type-validation`, base `cd7a3c1e262f217a05f337bfab4c8935fdc8f8d5`.

Sources: [mission](../../../../mission.md), [technical constraints](../../../../tech-stack.md), [roadmap Phase 72](../../../../roadmap.md#phase-72-drop-zone-type-validation), and the [HTML file-upload contract](https://html.spec.whatwg.org/multipage/input.html#file-upload-state-(type=file)).

## Evidence and delegated decisions

Phase 71 merged through PR #460 at the base after all seventeen checks passed. Phase 72 has no prerequisites. Shared `Forms` change handling currently lists files from a native input in a drop-zone label; native drop assignment belongs to the browser. `accept` is a picker hint rather than type constraint validation. Generic Forms validation uses `.validate` and direct-parent error text, which does not reach a zone-level sibling of the label. Native change does not cross shadow roots, while input does. Reset currently clears lists during capture before a later handler can cancel it.

The user delegated planning, requirements, specification review, implementation and feasible acceptance checks through feature-spec-auto, followed by incremental implementation, independent review/fixes, simplification and green PR merge. These are agent decisions from inspected evidence, not personal user approval.

Use an explicit boolean `data-validate-types` on the native file input inside `.drop-zone`. Existing `accept` supplies the allowed types. Unmarked zones retain their picker-hint behavior. Reuse `Forms.validateField(input)` for silent scripted validation; add no component or root export. Authors provide a direct zone-level `[data-error]` status area. Its optional nonempty data-error value localizes the type-rejection message; otherwise the runtime supplies a message naming accept. Use native custom validity for form prevention and real text for accessible inline feedback. File names and MIME labels are hints, not content inspection or a security boundary.

## Requirements

- **R1. Opt-in matching.** Only enabled native file inputs with data-validate-types inside their nearest drop-zone check accept. Match comma-separated alternatives after trimming, case-insensitively: filename suffix extensions, including multi-part suffixes, exact MIME types without parameters, and image/*, audio/* or video/*. Match at least one valid specifier per file. Do not infer MIME from filenames; empty MIME can match an explicit extension but fails MIME-only rules. Missing, empty or wholly unsupported/malformed accept values impose no type restriction; ignore unsupported tokens in a mixed list. Keep required-empty native invalidity and optional-empty validity. Disabled controls/fieldsets remain inactive.
- **R2. Reject the whole selection.** If any file fails, acquire native custom validity with an explanatory type message when there is no unrelated application custom error, and mark the input invalid with aria-invalid. Preserve a pre-existing unowned application message; type feedback and rejection reporting still explain the type failure separately. Retain the complete native FileList and list all selected filenames safely; never filter or replace it, upload, or emit an accepted subset. Validation works without a drop-zone-files list. An ordinary validated form cannot submit the invalid selection; existing native novalidate/formnovalidate and error-summary behavior remain intact.
- **R3. Accessible authored feedback.** Require a direct zone-level data-error area with role=status and aria-live=polite for the opt-in markup. Give it an id when missing and append that id once to aria-describedby, preserving author descriptions. Write messages with textContent. Show the type message while files fail matching; otherwise reflect any remaining native required/application invalidity, or hide/clear the area when valid. Keep focus with the native interaction; do not force focus or open a native validation bubble during file changes. Reuse error tokens and supporting-text typography for visible error treatment. Do not initialize components in static semantics checks.
- **R4. Consistent delivery and rejection event.** Browse and native drop both validate the native input's complete files through shared Forms handling, including dynamically inserted zones and open shadow roots. Native input/change pairs produce one rejection event for one changed selection. Emit a bubbling, composed, noncancelable expressive:reject from the nearest wrapper with `{ input, files, rejected, reason: 'type' }`, using array snapshots containing File objects. The event reports a type-rejected selection, not a request that can permit invalid files. A genuinely new selection can report again; duplicate native delivery of unchanged files/accept does not. Silent Forms.validateField calls emit no rejection event. Preserve ordinary native input/change events and legacy noncomposed document change handling.
- **R5. Recovery and ownership.** Valid replacement, clearing, removal of the opt-in followed by validation, and successful form reset remove framework-owned type validity and feedback. Never overwrite or clear an unrelated application custom validity message; acquire a native type message only when empty or framework-owned. Preserve an application error across invalid selection, valid replacement, clearing and reset. If an application replaces a framework message, subsequent recovery preserves that new value. Keep native required and application constraints effective. A canceled reset preserves selected files, list, validity, feedback and drag state. Perform reset cleanup after native reset and respect defaultPrevented, including shadow-root forms after their first handled selection. Keep independent/nested zones isolated. Reset and silent validation emit no rejection event; older processing must not overwrite a newer reentrant selection.
- **R6. Verified guidance.** Update drop-zone docs, llm.md and changelog with opt-in, supported matching/empty MIME, malformed hints, feedback, events, script/reset ownership and server-validation responsibilities. Regenerate semantics/skill/MCP guidance. Review JS/CSS gzip deltas and run focused Node, actual browser input, full contributor, MCP and isolated-package checks. Inspect applicable compact/expanded/large/dark visuals, complete independent final review and separate simplification, then satisfy exact-head CI/conversation/current-master/merge gates.

## Scope and evidence limits

Phase 73 owns per-file size limits; Phase 74 owns count limits. No uploads, content sniffing, MIME inference library, FileList filtering, drag-default override, new dependency or new component is added. Applications still validate received data on the server and own direct uploads or code that bypasses native form validation. Authors reserve the error area for runtime messages and can localize the type message through data-error.

Automation through setInputFiles or chooser.setFiles does not approve a physical OS picker. A synthetic drop does not perform native file assignment. Exercise native Chromium protocol drag delivery if supported; distinguish it from files assignment/input-change parity in Firefox/WebKit. Physical OS drag delivery, native zoom, hardware and spoken output remain unavailable. Keep roadmap completion labels unchanged here; the separate post-merge documentation PR records completion and final merge evidence.
