# ExpressiveCSS research brief for AI coding agents

## Authority and decision order

This brief separates **normative project rules** from **explanatory guidance**. For generated UI, use this order:

1. **Normative:** `semantics.json` is the source of truth for authored element choice, landmark structure, and implied ARIA; `SEMANTICS.md` is generated from it, and `tests/semantics.test.js` enforces the rules across `llm.md`, `docs/src`, `tests/fixtures.js`, and the forbid rules in `m3-guidelines.md`. All 54 roster rows are enforced. (`semantics.json`; `SEMANTICS.md`; `tests/semantics.test.js`)
2. **Normative public contract:** use the package exports, current source, and documented component markup/API as the truth for what ExpressiveCSS actually ships. (`package.json`; `src/ts/index.ts`; `src/ts/components/registry.ts`; `llm.md`; `docs/src/pages/`)
3. **Design contract / explanatory guidance:** use `m3-guidelines.md` to choose components, anatomy, placement, emphasis, and adaptive behavior. If it conflicts with the live Material specification, Material wins for design intent; `llm.md` still wins for the implementation ExpressiveCSS provides. (`m3-guidelines.md`)

Two documentation conflicts found during this research demonstrate why that order matters; both are now guarded by `tests/docs-astro.test.js`:

- The loading indicator was listed as not shipped even though the implementation contract, semantics roster, stylesheet, docs page, and tests expose `.loading-indicator`. The guide now treats it as shipped. (`llm.md`; `semantics.json`; `src/sass/components/_loading-indicator.scss`; `docs/src/pages/loading-indicator.astro`; `tests/loading-indicator.test.js`)
- The guideline cheat sheet named `button.circle` as the icon-button host even though the implementation has a distinct `.icon-button` component. The guide now uses `.icon-button` for the M3 icon-button token/size system and reserves `.button.circle` for the older round common-button form with different glyph sizing. (`llm.md`; `SEMANTICS.md`; `CLAUDE.md`; `src/sass/components/_icon-buttons.scss`)

## Installation and public assets/APIs

- Install with `npm install @expressivecss/expressive`; the supported runtime for building from source is Node 20 or newer. A source build is `npm install && npm run build`. The declared browser baseline is the last five Chrome and Firefox releases, with no IE/Edge Legacy support; the docs toolchain separately requires Node 22.12 or newer. (`llm.md`; `README.md`; `package.json`; `src/sass/README.md`)
- Public package entry points are `@expressivecss/expressive` for JavaScript and types, `/css` and `/css/min` for compiled styles, and `/scss` plus `/scss/*` for Sass. Published files comprise `dist`, `src/sass`, and `CHANGELOG.md`; do not import unpublished TypeScript source. (`package.json`; `llm.md`)
- The build emits ESM (`expressive.mjs`), CommonJS (`expressive.cjs`), browser IIFE (`expressive.js` / `expressive.min.js`), CSS, source maps, and declarations under `dist/`. The IIFE global is `Expressive`. (`README.md`; `package.json`)
- A minimal page needs the viewport meta tag, the ExpressiveCSS stylesheet, the JS bundle if interactive behavior is used, and initialization after markup exists. Material Symbols and the default Roboto/Noto Sans fonts are external assets and are **not shipped**; load them or deliberately replace the related font tokens. (`llm.md`; `CLAUDE.md`)
- The module’s supported exports include `AutoInit`, `Forms`, `version`, shared dialog/sheet behaviors, and the component classes re-exported from the component barrel. Consult the relevant `llm.md` or `docs/src/pages/<component>.astro` section for component-specific options and methods rather than guessing. (`src/ts/index.ts`; `src/ts/components/index.ts`; `llm.md`)

## Styling, tokens, and Sass

- **Normative project convention:** begin with semantic/native HTML, apply the documented component classes and required child structure, then use the framework’s single-purpose layout, spacing, alignment, visibility, color, and elevation utilities. Required classes and ID/data-target relationships are API because JavaScript queries them. (`llm.md`; component sources under `src/ts/components/`)
- Import Sass with `@use "@expressivecss/expressive/src/sass/expressive"` (or the package `/scss` export). The emitted cascade order is `tokens`, `base`, `components`, `utilities`; utilities intentionally outrank components, while ordinary unlayered application CSS outranks all framework layers. (`llm.md`; `src/sass/README.md`; `src/sass/expressive.scss`; `package.json`)
- Theme with `<html theme="light">` or `theme="dark"`; `theme="auto"` or no attribute follows the OS. Switching the attribute at runtime changes `color-scheme`. Consume live roles such as `--md-sys-color-surface`, `--md-sys-color-on-surface`, and `--md-sys-color-primary`, not hard-coded colors or the `-light`/`-dark` backing pairs. Set `--md-source` to generate the non-error tonal ramps; `vibrant` remaps surface roles for a subtree and should be rare. (`README.md`; `llm.md`; `src/sass/README.md`; `src/sass/tokens/_reference.scss`; `src/sass/tokens/_theme.scss`)
- For translucent token colors, use `color-mix(in oklab, var(--md-sys-color-primary) 6%, transparent)`. `rgba(var(--token), alpha)` is invalid because the tokens are complete colors, not channel lists. (`src/sass/README.md`)
- **Anti-patterns:** do not cross Sass file boundaries with `@extend`; use mixins or tokens. Do not make files in `abstracts/` emit selectors. When adding framework Sass, put component rules, utilities, shared abstractions, element defaults, and tokens in their documented directories and forward new partials through the appropriate index. (`src/sass/README.md`)
- The sheet supports shadow-root-only adoption. Any root-anchored token declaration must pair document and shadow hosts (for example `:root, :host`), and generated portals must remain in their originating root. (`src/sass/README.md`; `tests/shadow-dom.test.js`; `src/ts/core/utils.ts`)

## Component markup and JavaScript lifecycle

- **Normative:** copy a component’s documented HTML structure; never infer it from appearance. Use native controls where documented—especially `<button>`, links with real `href`s, `<input>`, `<select>`, `<progress>`, `<label>`, and native `<dialog>`. Preserve required child classes, IDs, `for`, `data-target`, and ARIA relationships. (`llm.md`; `semantics.json`; `docs/src/pages/`)
- Importing JavaScript installs shared Forms, Chips, Slider, Cards, ExpandingCard, Dialogs, BottomSheets, and SideSheets behaviors, but does **not** call `AutoInit()`. Call `AutoInit()` after markup exists, optionally with a context and per-component options. (`src/ts/index.ts`; `README.md`; `llm.md`)
- `AutoInit()` queries its registry beneath the supplied context (default `document.body`) and skips `.no-autoinit`. Do not combine `AutoInit()` and manual `Component.init()` on the same element; add `.no-autoinit` when passing manual options. The registry is the definitive selector list. (`src/ts/components/registry.ts`; `llm.md`)
- Current registry keys/selectors are: `Autocomplete` → `.autocomplete`; `Cards` → `article:has(> aside)`; `ExpandingCard` → `article.expanding-card:has(> dialog.expanding-card-dialog)`; `Carousel` → `.carousel`; `Chips` → `.chips`; `Datepicker` → `.datepicker, .date-picker`; `Menu` → `.menu-trigger`; `Lightbox` → `.lightboxed`; `ScrollSpy` → `.scrollspy`; `FormSelect` → `select`; `NavigationDrawer` → `.sidenav, .navigation-drawer`; `NavigationRail` → `.navigation-rail`; `Tabs` → `.tabs`; `Timepicker` → `.timepicker, .time-picker`; `Tooltip` → `.tooltipped`; and `FloatingActionButton` → `.fab, .fixed-action-btn, .fab-menu`. (`src/ts/components/registry.ts`; `src/ts/components/cards.ts`; `src/ts/components/expandingCard.ts`)
- Most per-element components follow `ComponentName.init(elementOrCollection, options)`, `ComponentName.getInstance(element)`, and `instance.destroy()`. Reinitialization destroys the old instance first. Instances are publicly stashed as `element.Expressive_<Component>`; upstream `M_<Component>` names are obsolete. (`src/ts/core/component.ts`; `src/ts/README.md`; `CLAUDE.md`)
- Destruction must remove listeners, generated DOM/state, and timers. Tests that schedule timers should always destroy in `finally`, because a surviving timer can keep Node’s test runner alive. (`src/ts/README.md`; `CLAUDE.md`; `tests/teardown.test.js`)
- Not every feature is a registry component. `Snackbar`, `CharacterCounter`, and `Slider` require their documented explicit/shared path; native dialogs use `showModal()` / `show()` and `close()`, with framework behavior layered onto them. (`src/ts/components/registry.ts`; `src/ts/README.md`; `llm.md`)

## Material 3 and adaptive decisions

- **Design contract:** choose a window size class, then one component per job. Do not stack peer navigation patterns, duplicate feedback mechanisms, or multiple high-emphasis actions in one region. Use sentence case, role colors, framework state layers, and one filled/FAB-level action per region. (`m3-guidelines.md`)
- Window classes and grid prefixes are Compact `<600px` / `.s`, Medium `600–839px` / `.m`, Expanded `840–1199px` / `.l`, Large `1200–1599px` / `.xl`, and Extra-large `>=1600px` / `.xxl`. Reason in window widths, not device labels; a landscape phone can be Expanded and a narrow desktop window Compact. (`m3-guidelines.md`; `llm.md`; `src/sass/abstracts/_breakpoints.scss`)
- Compact layouts normally use one pane and a navigation bar; Medium may use a bar or collapsed rail; Expanded and larger favor rails and two-pane list/detail where appropriate. Never render a bar and rail together or a fixed drawer beside a rail. Compact list/detail shows one active pane and a back action; Expanded+ splits the panes. (`m3-guidelines.md`; `docs/src/pages/panes.astro`)
- Choose feedback by urgency: dialogs block high-priority work, snackbars report ignorable status, bottom sheets suit compact transient actions, menus suit the same job from Medium upward, and standard side sheets hold optional persistent content at Expanded+. (`m3-guidelines.md`)
- Use only shipped components and current ExpressiveCSS names. Do not resurrect Materialize/M2 classes such as `btn`, `modal`, `nav-wrapper`, `brand-logo`, `card-content`, `lever`, `filled-in`, or `with-gap`, and do not fake a Material component listed as not shipped. (`m3-guidelines.md`; `CLAUDE.md`)

## Accessibility and HTML semantics

- **Normative:** authors own static semantics; the framework owns dynamic state. Do not pre-author values such as `aria-expanded` where the component sets and updates them. Only declare a composite ARIA role when its keyboard contract is implemented and tested. (`semantics.json`; `SEMANTICS.md`)
- Icons are `<span class="material-symbols" aria-hidden="true">`; a decorative ligature must not become the control’s spoken name. Every icon-only control needs a non-empty accessible name, normally `aria-label`, and should have a tooltip when no visible text explains it. (`semantics.json`; `SEMANTICS.md`; `m3-guidelines.md`)
- Use `<nav>` only for destinations, label every navigation landmark, and never nest `<main>`. Card/banner action rows, toolbars, button groups, and bottom app bars contain commands and are not navigation or authored composite widgets. (`semantics.json`; `SEMANTICS.md`)
- ExpressiveCSS tabs are in-page navigation links with `aria-current`, **not** an authored `tablist`; carousels follow the ARIA carousel pattern rather than tabs. Active navigation-bar, drawer, and rail destinations likewise need `aria-current="page"`; a painted `.active` class is insufficient. (`semantics.json`; `SEMANTICS.md`)
- Preserve native state and naming: every form field needs its real `<label>` relationship; buttons inside forms need the correct `type`; images need an `alt` attribute; live loading indicators need `role="status"` plus a name; hidden subtrees must not retain focusable descendants. (`semantics.json`; `SEMANTICS.md`; `m3-guidelines.md`)
- Framework-generated user-facing strings expose `i18n` options. Do not replace them with hard-coded English inside component source. (`semantics.json`; `src/ts/core/component.ts`; component option types under `src/ts/components/`)
- **Accessibility boundary:** the project semantics contract deliberately excludes keyboard interaction, focus management, and color contrast, so passing `tests/semantics.test.js` is not full accessibility conformance. Separately verify that all functionality is keyboard operable (WCAG 2.2 SC 2.1.1), keyboard focus is visible (SC 2.4.7), normal text reaches 4.5:1 and large text 3:1 (SC 1.4.3), and identifying UI/graphic parts reach 3:1 against adjacent colors (SC 1.4.11). ([W3C WCAG 2.2](https://www.w3.org/TR/WCAG22/); [WAI: Keyboard](https://www.w3.org/WAI/WCAG22/Understanding/keyboard-accessible); [WAI: Focus Visible](https://www.w3.org/WAI/WCAG22/Understanding/focus-visible.html); [WAI: Contrast Minimum](https://www.w3.org/WAI/WCAG22/Understanding/contrast-minimum.html); [WAI: Non-text Contrast](https://www.w3.org/WAI/WCAG22/Understanding/non-text-contrast.html); project scope: `semantics.json`; `SEMANTICS.md`)

## Testing and verification

- Run `npm test` and `npm run typecheck`. `npm test` rebuilds every JS format and CSS before the Node `node:test` + jsdom suite, avoiding stale-`dist` false results. (`README.md`; `package.json`; `CLAUDE.md`)
- jsdom has no layout engine. Assert DOM structure, content, classes, options, lifecycle, and event behavior; stub geometry explicitly when needed. Do not assert real geometry, visibility, or transitions in unit tests. (`README.md`; `src/ts/README.md`; `CLAUDE.md`; `tests/setup.js`)
- A new auto-init component needs an independent minimal fixture in `tests/fixtures.js`; do not derive the fixture from the registry, because the test must catch a wrong selector. Behavior changes need focused component/regression tests; teardown, hot-path, injection, shadow DOM, token/color, generated accessibility, and semantic suites protect their named contracts. (`README.md`; `src/ts/README.md`; `CLAUDE.md`; `tests/fixtures.js`; `tests/semantics.test.js`)
- For visual changes, use `npm run test:visual`; it compares the working tree with its merge base rather than committed baselines. (`package.json`; `CLAUDE.md`)
- Before handing off generated UI, verify: the next narrower layout, exactly one persistent navigation pattern, at most one high-emphasis action per region, the correct feedback surface, accessible icon controls and labelled fields, role tokens rather than hex, one-pane compact list/detail behavior, no legacy classes, and exactly one initialization path per registry component. (`m3-guidelines.md`)
- Exercise keyboard-only operation, visible focus, modal focus return/Escape behavior, zoom/reflow, light and dark themes, reduced motion, and text/non-text contrast in a real browser; jsdom and the semantics checker cannot prove these. (`semantics.json`; `CLAUDE.md`; [W3C WCAG 2.2](https://www.w3.org/TR/WCAG22/))

## High-value anti-pattern checklist

Do not invent markup or legacy class names; hard-code colors; consume theme-specific backing tokens; initialize twice; assume import equals auto-init; add unimplemented ARIA composite roles; use links for commands or `<nav>` for action rows; leave icon-only controls unnamed; keep focusable content under `aria-hidden`; show peer navigation components together; force multiple panes on Compact; use dialogs for “Saved” or snackbars for destructive confirmation; make switches wait for Save; write JS-driven `transform`, `opacity`, `display`, or overflow over components whose CSS/state attributes own those properties; append generated overlays outside the originating shadow root; or test a stale build. (`llm.md`; `m3-guidelines.md`; `semantics.json`; `src/ts/README.md`; `src/sass/README.md`; `CLAUDE.md`)
