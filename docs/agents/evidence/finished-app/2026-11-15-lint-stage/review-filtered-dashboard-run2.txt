CHECKED
- Lifecycle: one `Expressive.AutoInit()` at `DOMContentLoaded`, after the markup and generated rows exist. There are no manual `.init()` calls, no `no-autoinit` conflicts, no retired global `M`, and no dynamic remounting, so there is nothing to destroy. `DataTables.sync` and `showPage` exist in the shipped bundle (dist/js/expressive.js:5030).
- Assets: `dist/css/expressive.min.css`, `dist/js/expressive.min.js` and `dist/fonts/` all exist in the expected layout. There are no Google Fonts or Material Icons stylesheets and no `.material-icons` markup. Only outlined `.material-symbols` are used. The script sits at the end of `<body>`, so it doesn't block rendering from `<head>`. The JS bundle is warranted, since tabs and data-table use the runtime.
- States: page buttons get `aria-disabled` from the framework, which ignores clicks on them while disabled (bundle 5168-5169, 5288). Native controls aren't class-disabled. No custom CSS removes focus rings. The search empty state has a Clear action that puts focus back on the search field. The count and page outputs are named live regions. Loading/error states don't apply because the data is inline and synchronous.
- WCAG from source: every icon is `aria-hidden`. The icon-only page buttons have `aria-label`. The search fields have `<label>`s. Each tab's nav, pagination nav and scroll region is named. The skip link targets a `main` with `tabindex="-1"`. Nothing sticky can hide focus (no `max-block-size`, no app bar). Reduced motion is handled by the tabs indicator spring, and the page adds no custom motion.
- finished-app:loading: not applicable (no command that runs a request in script).
- finished-app:destructive: not applicable (no remove or discard actions).
- finished-app:url-state: on load, `view`, `q` and `page` are restored. Search and page are written with `replaceState`, and page resets on filter, which matches the bundle (`_resetPage`, 5284). Writing the tab on `expressive:change` passes. The one failure is the finding above.
- finished-app:submit-flow: not applicable (no form). The search fields have `name`, `type="search"`, `autocomplete="off"`, `spellcheck="false"`, and the floating-label `placeholder=" "`.

BLOCKED
- Text and UI-boundary contrast (on-surface-variant body text, tab labels, outlined field, pager status) in light and dark: no browser route.
- Target size (2.5.8) of the sort header buttons in a `dense` table and of the pager icon buttons: needs rendered measurement.
- Visible focus on the tab links, sort buttons, the focusable `.data-table` region and the pager buttons: needs a render.
- Whether a screen reader announces `aria-disabled` pager buttons and the `output` live regions as expected: needs browser and assistive-technology evidence.
- Edge case I couldn't settle: a URL with both `?view=` and a tab hash. Tabs prefers `location.hash` (bundle 15782), so the view may disagree with `view=` on load. The app's own writes never produce that URL.

HANDOFFS
- Layout: the `.data-table` wrappers have no `max-block-size`, so the sticky header never engages. A 10-row dense page is probably fine.
- Markup: the toolbar and footer sit inside the focusable `role="region"` scroll wrapper. Allowed by the filter contract, but worth confirming the region's name and focus stop still make sense with controls inside.
