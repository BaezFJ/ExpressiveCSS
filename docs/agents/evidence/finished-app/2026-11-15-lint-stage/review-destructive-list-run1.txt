- [major] index.html:232-253 (submit handler, `try { await request(...) } finally {...}`) | source | finished-app:submit-flow; error state (check 3) | The `try` has no `catch`. The `else` snackbar never runs, so the person sees the dialog go back to "Save address" with no error. | Add `catch { added = null; }`, or move the failure snackbar into a `catch` so both a non-ok response and a rejected request show the error.
- [major] index.html:252 (`new Expressive.Snackbar({ text: "Couldn't save the address. - [major] index.html:82, 227-229 (`#save-add`) | source | finished-app:loading | While the POST runs, the button changes to "Saving…" and sets `aria-busy`, but nothing shows progress beside the label. - [major] index.html:172-198 (deferred DELETE: `completeCallback: commit` plus `pagehide` → `commit()`) | source | finished-app:destructive | A Snackbar with an action defaults to `displayLength: Infinity`, so the DELETE waits until the bar is dismissed, replaced, or the page is hidden. Undo itself restores the row in place, in id order. | Send the request with `fetch(..., { keepalive: true })` or `navigator.sendBeacon` on `pagehide`. - [polish] index.html:81, 212-213 and fields 61-76 during `saving` | source | state (check 3) | While a save is running, Cancel looks enabled but does nothing (`if (!saving)`), and Escape is blocked. The fields stay editable, but `FormData` was captured before the `await`, so edits made during the wait are silently dropped. | During the save, set `disabled` on Cancel and the fields (or `inert` on the field group), and restore them in `finally`.

CHECKED
- Lifecycle: one `Expressive.AutoInit()` on DOMContentLoaded, after `render()`. The script sits at the end of `body`. There are no registry components to init twice and no global `M`. Dynamic rows hold only plain buttons that need no init. Snackbar is used through its explicit path. The `pagehide` listener is removed on both the Undo and commit paths.
- Assets: dist/css/expressive.min.css, dist/js/expressive.min.js and dist/fonts/* all exist. There is no Google Fonts or Material Icons link and no `.material-icons` markup. Only outlined `.material-symbols` is used. The JS bundle is needed (Snackbar, Forms). No render-blocking script is in `head`.
- States: no CSS removes focus rings and no control is disabled with a class. The list has an empty state (`#empty-state`). The initial data is inline, so no loading state is needed on load. Double press on delete is guarded (`event.detail > 1`), and so is double submit (`saving`).
- WCAG (source): icon-only delete buttons are named ("Delete {label} address") and decorative icons are hidden. The dialog is named by `aria-labelledby`. Labels use `for`, and help and error text is linked through `aria-describedby` (`Forms.validateField` adds the `[data-error]` element). Focus moves to a neighbouring delete button or the empty-state button after a delete, to the restored row after Undo, and to the new row after an add. Nothing is sticky, so there is no 2.4.11 risk from the page itself. Dialog motion respects reduced motion according to its guide.
- finished-app:loading: covered by the findings above.
- finished-app:destructive: delete takes effect at once with Undo (`replace: true`), and restore re-inserts by id order, which matches list order. The failure path restores the row and announces it.
- finished-app:url-state: not applicable (no tabs, filters, search or pages).
- finished-app:submit-flow: `<form>` with a submit button, so Enter submits. The submit button is never disabled before submission. Errors sit at their fields, and the first invalid field gets focus. Paste is not blocked. `autocomplete` is set to address-line1, address-level2 and postal-code; "Label" is not an input-purpose field. Every field has a `name`. `spellcheck="false"` is on the postal code. `placeholder=" "` is part of the floating-label markup.
