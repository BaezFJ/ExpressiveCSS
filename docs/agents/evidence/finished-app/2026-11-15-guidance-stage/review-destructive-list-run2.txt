FINDINGS
- [major] index.html:100 (`#address-form` Cancel button, before `#save-button` at line 104) | source | finished-app:submit-flow | Pressing Enter in any dialog field cancels instead of saving. The seven inputs belong to `#address-form` through the `form` attribute, so Enter clicks the form's default button. That is the first submit button in tree order, which is Cancel (`type="submit" value="cancel" formnovalidate`). The submit handler sees `submitter.value === 'cancel'` and lets `method="dialog"` close the dialog, so everything typed is lost. | Make Cancel `type="button"` and close the dialog with `dialog.close('cancel')` from a click handler. Leave Save as the only submit button so Enter submits through it. You could also move the fields inside the `<form>` and put Save first in tree order.
- [polish] index.html:228-229 (`commit` catch path in `deleteAddress`) | source | finished-app:destructive | When a DELETE fails, the error Snackbar uses `replace: true`. That cuts short the Undo bar of any row deleted after it, and the cut-short bar runs its `completeCallback`, which commits that second row's DELETE straight away. Example: delete A, then delete B, and A's request fails about 800 ms later. B's Undo disappears and B is committed without the person choosing that. | Leave out `replace: true` on the failure snackbar so it waits behind the Undo bar, or report the failure inline so the pending Undo stays.
- [polish] index.html:216 with 228 (`restore()` called from `commit` failure) | source | - | `restore()` always calls `focusDelete(item.id)`. When it runs because a background DELETE failed, it moves keyboard focus to the restored row from wherever the person is working. | Pass a flag so only the Undo path moves focus. On the failure path, announce the problem without moving focus.
- [polish] index.html:247-249 (`pagehide` commit) | source | - | A pending delete is sent only when its Undo bar is dismissed, replaced, or on `pagehide`. An action snackbar stays up indefinitely by default, and `pagehide` does not fire reliably when a mobile browser discards a backgrounded tab. A row the person saw deleted can come back on the next visit. | Also commit on `visibilitychange` when `document.visibilityState === 'hidden'`, or give the Undo bar a finite `displayLength` backed by persistent feedback.

BLOCKED

- Focus not obscured (2.4.11): needs a browser to see whether the persistent Undo snackbar at the bottom covers the last row's focused delete button.
- Whether a Snackbar shown with `replace: true` takes focus when it appears. The guide says a queued snackbar captures focus. If an immediate one does too, it would override the focus moved to the next row's delete button after a delete.

- Reduced motion: the page adds no motion of its own. How the framework's snackbar and dialog motion responds was not checked.
