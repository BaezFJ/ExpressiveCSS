CHECKED
- Lifecycle: the script loads at the end of `<body>` after the markup. `AutoInit()` is called once, after the first `render()`. Rendered rows contain only CSS-only icon buttons, so nothing in them needs initializing or destroying. Snackbar is created through its own explicit path. The retired global `M` is not used, and there is no manual `.init()` or second `AutoInit()`.
- Assets and fonts: the page links one compiled stylesheet, `dist/css/expressive.min.css`, and `dist/fonts/` sits next to `dist/css/`. There are no Google Fonts links, no Material Icons stylesheet and no `.material-icons` markup. Icons use `.material-symbols` with `aria-hidden="true"`. The JS bundle is needed for Snackbar, and no script blocks rendering from `<head>`.
- States: no custom CSS removes the focus ring. No native control is disabled with a class. The list has an empty state (`#empty-state`), and focus moves to its action when the last row is removed. Save has loading and error handling (see the error finding above). A failed delete puts the row back and shows a snackbar. The initial data is in memory, so the list needs no loading state.
- WCAG names, labels and keyboard (source): every delete icon button has `aria-label="Delete <label> address"`. Fields have `<label for>`, and errors are tied to their fields through `aria-describedby` and `aria-invalid`, with each message naming its field. The dialog focuses the first field when it opens and returns focus when it closes. Focus moves to the next row, the previous row, or the empty-state action when a row is removed, and back to the row after Undo.
- finished-app:loading: Save keeps a label that names the action ("Saving…" ends in …). A `.loading-indicator` appears beside the actions after 300 ms and stays at least 500 ms. The `saving` guard ignores a second submit, and Cancel and Escape are blocked while saving. Delete is optimistic with Undo, so it is judged under destructive.
- finished-app:destructive: delete removes the row at once and offers an Undo snackbar with `onAction` and `replace: true`. Undo puts the row back in front of the row that followed it. Because `replace: true` commits any earlier pending delete, the following row is still there whenever Undo is available. The `undone` flag keeps `completeCallback` from committing after Undo. Pending deletes are committed on `pagehide`. The `event.detail > 1` guard stops a double click from deleting the next row.
- finished-app:url-state: not applicable, because the page has no tabs, filters, search or pages.
- finished-app:submit-flow: the fields are inside `<form>`, and Save is a submit button connected with `form="address-form"`, so Enter submits. Save is not disabled before submitting. A failed submit moves focus to the first invalid field. Nothing blocks paste. Autocomplete is set: `street-address`, `address-level2` and `postal-code`, with `off` on the custom label field, which is not an input-purpose field. Every field has a `name`. Floating-label `placeholder=" "` passes.

- The real network failure paths: the stub always succeeds, and the `pagehide` commit calls the 800 ms stub instead of `fetch(..., { keepalive: true })`, so with a real server it would probably not get sent before the page unloads. I could only judge these by reading the code.
